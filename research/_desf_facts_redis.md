## 33. Desfășurări `redis`: atomicitate, structuri, TTL și evacuare, persistență, Pub/Sub și Streams, cache-aside, lock, rate limiting, KEYS / SCAN, Valkey (tichetul 17; verificat 3 noiembrie 2026)

Python rulat pe 3.13.16 (blocurile din `src/desf/redis.md` rulează în `node tools/desf_examples.mjs`; sunt simulări în Python pur, fiindcă check-ul nu pornește un server). Comenzile Redis din blocurile `text` au fost rulate de mână pe **Redis server 7.0.15** (`redis-server` din mediu, port temporar, fără persistență) cu `redis-cli` și `redis-py` 8.1.0. C++: `g++ -std=c++11 -pthread`. Fapte complementare: secțiunea 13 (lock `SET NX PX`, rate limiter cu `INCR`, cache-aside) și 26 (backpressure, rate limit în design).

- ✅ **Un singur thread pentru comenzi** (https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/benchmarks/): „Redis is, mostly, a single-threaded server from the POV of commands execution (actually modern versions of Redis use threads for different things). It is not designed to benefit from multiple CPU cores.” Pentru scalare pe nuclee se pornesc mai multe instanțe. Desfășurarea spune doar „versiunile noi fac alte treburi cu thread-uri; comenzile rămân pe unul”, fără să numească I/O threads.
- ✅ **`INCR`** (https://redis.io/docs/latest/commands/incr/): cheia lipsă se pune pe 0 înainte; limitat la întregi pe 64 de biți cu semn; „this is a string operation”. Rulat: `INCR` pe o cheie inexistentă dă 1; pe un string ne-numeric dă „value is not an integer or out of range”.
- ✅ **`MULTI`/`EXEC` fără rollback**: rulat (`redis-py`, `pipeline(transaction=True)`): `SET a 1`, `INCR s` (pe un string `abc`), `SET b 2` → `[True, ResponseError, True]`, iar după `EXEC` `a` = 1 și `b` = 2 (comenzile bune au rulat, cea greșită a dat eroare). Concordă cu explicația RD-08.
- ✅ **TTL** (https://redis.io/docs/latest/commands/expire/): TTL-ul se șterge doar de comenzile care șterg sau suprascriu cheia (`DEL`, `SET`, `GETSET`, `*STORE`); `INCR`, `LPUSH`, `HSET` îl lasă neatins. Expirare pasivă (la acces) și activă (Redis testează periodic chei la întâmplare dintre cele cu TTL). Rulat: `SET k 5 EX 100`, `INCR k` → 6, `TTL k` → 100, `SET k 7`, `TTL k` → -1.
- ✅ **`maxmemory` și politici** (https://redis.io/docs/latest/develop/reference/eviction/): `maxmemory 0` = fără limită (implicit pe 64 de biți); `noeviction`: „the server will return an error when you try to execute commands that cache new data”, citirile merg; `allkeys-lru` e „a good default option” când un subset de chei e citit mult mai des; `volatile-*` aleg doar dintre cheile cu TTL și se comportă ca `noeviction` fără chei cu TTL. Rulat: `CONFIG GET maxmemory-policy` → `noeviction`, `maxmemory` → 0 (7.0.15); cu `maxmemory 3mb` și `noeviction`, scrierile pică cu „command not allowed when used memory > 'maxmemory'.” (după ~2765 de chei de 500 de octeți), iar cu `allkeys-lru` toate cele 20000 de scrieri trec. ⚠️ Valoarea implicită `noeviction` e verificată prin rulare pe 7.0.15; pagina de docs nu o numește „implicit”. Politicile `*-lrm` apar din Redis 8.6 (nu sunt folosite în desfășurare).
- ✅ **Persistență** (https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/): RDB = snapshot la intervale (fork; pierzi „the latest minutes of data”); AOF = jurnal de comenzi rejucat la pornire; `appendfsync always` / `everysec` / `no`, „the suggested (and default) policy is to fsync every second”, cu risc de pierdere „one second worth of writes”; RDB + AOF împreună: „In the case both AOF and RDB persistence are enabled and Redis restarts the AOF file will be used”; documentația recomandă ambele pentru siguranță „comparable to what PostgreSQL can provide”; fără persistență e permis la cache. Implicit Redis salvează snapshot-uri în `dump.rdb`. Rulat pe 7.0.15 (pornit fără configurare): `save` = `3600 1 300 100 60 10000`, `appendonly` = `no`, `appendfsync` = `everysec`. Multi-part AOF din 7.0.
- ✅ **Pub/Sub** (https://redis.io/docs/latest/develop/pubsub/): „at-most-once message delivery semantics”; dacă abonatul nu poate procesa mesajul (eroare sau deconectare) „the message is forever lost”; pentru garanții mai tari se recomandă Streams. Rulat: `PUBLISH news hello` fără abonați → 0 (numărul de abonați care au primit mesajul).
- ✅ **Streams și consumer groups**: rulat pe 7.0.15 (`redis-py`): `XGROUP CREATE jobs g1 $ MKSTREAM`, două `XADD`, `XREADGROUP` de `w1` cu `COUNT 1` → prima intrare; `XPENDING` → 1 în pending la `w1`; după 200 ms `XAUTOCLAIM jobs g1 w2 100 0-0` → `w2` preia intrarea; `XACK` → 1; pending → 0; `XLEN` rămâne 2 (intrările rămân în stream după citire și ack). ⚠️ Pagina Streams (277 000 de caractere) a fost citită doar în primele 100 000; semantica `XREADGROUP`/`PEL`/`XAUTOCLAIM` e din rulare, nu citată din prosa paginii. Pagina de Pub/Sub spune că Streams suportă „both at-most-once as well as at-least-once”.
- ⚠️ **Cache-aside și stampede** sunt tipare, nu comenzi (secțiunea 13: „scrii sursa, apoi ștergi cheia” nu elimină o citire concurentă care repune o valoare veche). Single-flight și TTL cu jitter sunt remedii obișnuite, neluate dintr-o pagină de docs Redis; exemplul din desfășurare (5 cereri care văd cache-ul gol) e o simulare.
- ✅ **Lock distribuit** (https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/): `SET resource_name my_random_value NX PX 30000`; valoarea „must be unique across all clients and all lock requests”; eliberare doar dacă valoarea e a ta, cu `DELEX key IFEQ my_random_value` (nou în **Redis 8.4**) sau, mai vechi, un script Lua cu `get` și `del`; „Using just DEL is not safe as a client may remove another client's lock”; „You should implement fencing tokens”; Redis nu folosește ceas monoton pentru TTL. Replicarea asincronă poate încălca excluderea mutuală la failover (aceeași pagină, „Why Failover-based Implementations Are Not Enough”). Fencing token (Kleppmann, https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html): „a fencing token is simply a number that increases” la fiecare achiziție; resursa protejată reține cel mai mare token văzut și respinge scrierile cu unul mai mic. Rulat: `SET lock tokA NX PX 30000` → OK; `SET lock tokB NX PX 30000` → nil; scriptul Lua de eliberare cu `tokB` → 0, cu `tokA` → 1.
- ✅ **Rate limiting** (https://redis.io/docs/latest/commands/incr/): varianta 1 cu `MULTI` / `INCR` / `EXPIRE` / `EXEC`; la `INCR` fără `EXPIRE` cheia „will be leaked” dacă clientul cade între ele (soluție: script Lua); `INCR` și `EXPIRE` în `MULTI` sunt atomice. Defectul ferestrei fixe (până la 2× limita la graniță) e raționament, simulat în exemplu (5 cereri la secunda 59 și 5 la 60 → 10 admise cu limita 5 pe minut). Sliding window cu sorted set: rulat `ZADD` / `ZREMRANGEBYSCORE` / `ZCARD` (4 intrări rămase în fereastră). Token bucket cu Lua: rulat un script `get` / `set` care scade jetonii (`[1, 1, 1, 0, 0]` la 3 jetoane). 429: RFC 6585 (secțiunea 23).
- ✅ **`KEYS` și `SCAN`** (https://redis.io/docs/latest/develop/using-commands/keyspace/ și https://redis.io/docs/latest/commands/scan/): `KEYS` „will block the Redis server until all keys are returned”, „intended for debugging and special operations”; `SCAN` poate fi folosit în producție, fără blocarea pe care o au `KEYS` sau `SMEMBERS`; ciclu complet = de la cursor 0 până când cursorul revine 0; „A given element may be returned multiple times”; elementele care nu au fost prezente tot timpul iterației pot sau nu să fie întoarse; `COUNT` implicit 10. Rulat (5 chei `u:*`): `SCAN 0 MATCH u:* COUNT 2` → cursor 5 și `u:3`, `u:1`; `SCAN 0 MATCH u:* COUNT 100` → cursor 0 și toate cele 5. Cursorul concret (5) depinde de tabela de hash; în desfășurare apare ca exemplu de la 7.0.15.
- ✅ **Valkey și licențe**: Redis 7.2.x și mai vechi sub BSD-3; 7.4–7.8 sub RSALv2 sau SSPLv1 la alegere; din 8.0 tri-licență RSALv2 / SSPLv1 / AGPLv3 (https://github.com/redis/redis, README). Valkey: „open source (BSD) high-performance key/value datastore”, „backed by the Linux Foundation” (https://valkey.io/); „compatible with Redis OSS 7.2 and all earlier open-source Redis versions”, iar „existing Redis client libraries can connect to Valkey without code changes”; Redis CE 7.4+ nu e compatibil (fișierele de date) (https://valkey.io/topics/migration/); AWS: „Amazon ElastiCache for Valkey, a serverless, fully managed caching service” (https://aws.amazon.com/elasticache/what-is-valkey/). ⚠️ Versiuni curente văzute azi: Valkey 9.1.3 (26 octombrie 2026, valkey.io); Redis 8.8 pe redis.io și 8.10.x în docs (BACKUP din 8.10.0); nu sunt scrise în desfășurare. „Fork al Redis 7.2.4, martie 2024” e din surse secundare (Phoronix, Wikipedia), de aceea desfășurarea spune doar „fork al Redis” și „compatibil cu 7.2”.
- ✅ **C++ (punctul 1)**: compilat cu `g++ -std=c++11 -pthread`: 4 thread-uri × 100 000 `fetch_add(1)` pe un `std::atomic<int>` dau 400000; `load()` de două ori, apoi două `store()` secvențiale (`GET`, `GET`, `SET`, `SET`) dau 1, nu 2. `std::atomic<T>::fetch_add` e o operație atomică de citire-modificare-scriere (C++11, `[atomics.types.operations]`); nu am cerut cppreference (403 din mediu).

**Erori de fapt în punctele fișei `redis`**: niciuna găsită. Cele 10 puncte au fost recitite față de sursele de mai sus și față de rulări. Precizări, nu erori: la 1, „un singur thread” se referă la execuția comenzilor (versiunile moderne folosesc thread-uri pentru alte treburi) și atomicitatea acoperă o comandă, nu două; la 3, `noeviction` e implicit, dar contează doar când `maxmemory` e setat (implicit 0, fără limită); la 4, implicit RDB e pornit și AOF oprit (7.0.15); la 7, `DELEX ... IFEQ` există din Redis 8.4, iar înainte e nevoie de Lua; la 10, Redis e din nou open source din 8.0 (AGPLv3 adăugat), deci Valkey nu mai e singura variantă open source.
