## 35. Desfășurări `docker`: imagine și container, cache de layere, multi-stage, .dockerignore / user / secrete, exec form și PID 1, healthcheck și volume, Compose, Swarm / Kubernetes / ECS / EKS, slim vs alpine (tichetul 18; verificat 3 noiembrie 2026)

Rulat local: Docker Engine 29.9.1 (daemon pornit cu `dockerd` în sandbox, containere reale), Docker Compose v5.6.0, imagini `alpine:3.20`, `python:3.13-slim` (Debian 13 „trixie”) și `python:3.13-alpine`, pip 26.2.2. Exemplele din `src/desf/docker.md` sunt blocuri ```text (Dockerfile, shell, YAML), deci nu le rulează `desf_examples.mjs`; rezultatele de după `# →` din ele vin din rulările de mai jos. Containerele din sandbox ajung la PyPI doar cu certificatul proxy-ului (montat și dat lui pip prin `PIP_CERT`).

- ✅ **Imagine, container, namespaces, cgroups** (https://docs.docker.com/get-started/docker-overview/, https://docs.docker.com/engine/containers/resource_constraints/): „An image is a read-only template with instructions for creating a Docker container”; „A container is a runnable instance of an image”; „Docker uses a technology called `namespaces` to provide the isolated workspace called the container”; la limitele de resurse „Docker modifies the settings for the container's cgroup on the host machine”; implicit „a container has no resource constraints”.
  - Rulat: `docker run --name c1 alpine sh -c 'echo hi > /tmp/x'` → `docker diff c1` arată `C /tmp` și `A /tmp/x`; după `docker rm c1`, un container nou din aceeași imagine nu are `/tmp/x` (`No such file or directory`). Cu un volum numit (`-v v1:/data`), fișierul scris de un container e citit de următorul.
- ⚠️ **Layere: „câte unul per instrucțiune” e aproximativ** (rulat: Dockerfile cu `ENV`, `WORKDIR`, `COPY`, `RUN`, `CMD` peste `alpine:3.20`): `docker history` are 7 intrări, dar `docker image inspect` numără 4 layere de sistem de fișiere (baza + `WORKDIR` care a creat `/app` + `COPY` + `RUN`); `ENV` și `CMD` apar cu 0 B, doar metadate. Documentația se contrazice: https://docs.docker.com/build/cache/ spune „Each instruction in this Dockerfile translates to a layer”, iar https://docs.docker.com/build/building/best-practices/ „Each `ENV` line creates a new intermediate layer, just like `RUN` commands”. Desfășurarea scrie versiunea măsurată (layere pentru instrucțiunile care schimbă fișiere, metadate pentru `ENV` / `CMD`); punctul fișei a fost corectat la fel.
- ✅ **Cache de layere** (https://docs.docker.com/build/cache/): „Whenever a layer changes, that layer will need to be re-built”; „If a layer changes, all other layers that come after it are also affected”; „Even if they wouldn't build anything differently, they still need to re-run”. Rulat (BuildKit): a doua rulare fără schimbări → toate layerele `CACHED`; după ce `a.txt` s-a schimbat, `WORKDIR` rămâne `CACHED`, iar `COPY a.txt .` și `RUN echo hi > b.txt` se reiau, deși comanda din `RUN` e aceeași.
- ✅ **Multi-stage** (https://docs.docker.com/build/building/best-practices/, https://docs.docker.com/get-started/docker-concepts/building-images/multi-stage-builds/): „Multi-stage builds let you reduce the size of your final image”; `FROM … AS nume`, `COPY --from=<etapă>`. Rulat (demonstrație cu `dd` în loc de compilator, fiindcă `apk` nu ajunge la rețea în build din sandbox): imaginea cu un singur stage și 200 MB creați în `RUN` are 222 MB, imaginea multi-stage care copiază doar un fișier mic are 12,1 MB și nu conține `/big`.
  - ⚠️ Dockerfile-ul din desfășurare (`pip install --prefix=/install` în etapa de build, `COPY --from=build /install /usr/local`) nu a fost construit aici; e același tipar ca referința `katas/skel_docker.Dockerfile` (verificată structural în `katas/test_skel_docker.py`) și ca exemplul din documentație.
- ✅ **`.dockerignore`, `USER`, secrete** (https://docs.docker.com/reference/dockerfile/, https://docs.docker.com/build/building/best-practices/, https://docs.docker.com/engine/swarm/secrets/): „You can use `.dockerignore` file to exclude files and directories from the build context”; „The `USER` instruction sets the user name (or UID) … to use as the default user”; „If a service can run without privileges, use `USER` to change to a non-root”; „Unlike `ENV`, an `ARG` variable is not embedded in the image and is not available in the final container” și „`ENV` values are always persisted in the built image”.
  - Rulat: `docker build --build-arg TOKEN=abc123` cu `ARG TOKEN` + `RUN echo "build $TOKEN"` → `docker history --no-trunc` arată `RUN |1 TOKEN=abc123 /bin/sh -c …` și `ARG TOKEN=abc123`; `ENV DB_PASS=s3cret` apare în `docker image inspect` la `Config.Env` și în istoric. Deci „ARG nu e în imagine” (documentația) nu înseamnă „valoarea nu se vede”: istoricul o păstrează când un `RUN` o folosește.
  - Rulat: `RUN --mount=type=secret,id=tok …` cu `docker build --secret id=tok,src=tok.txt` → valoarea nu apare în `docker history` (0 potriviri pentru `abc123`).
  - Swarm: secretul e „mounted into the container in an in-memory filesystem”, implicit la `/run/secrets/<nume>`, nu se păstrează în imagine și „can not be committed to an image” prin `docker commit`; „encrypted during transit and at rest in a Docker swarm” (cu excepția containerelor Windows).
  - ⚠️ `useradd` în Dockerfile: referința `katas/skel_docker.Dockerfile` o folosește (verificată structural); nu am construit un Dockerfile cu `USER` aici.
- ✅ **Exec form, PID 1, SIGTERM** (https://docs.docker.com/reference/dockerfile/ la `ENTRYPOINT`; https://docs.docker.com/reference/cli/docker/container/stop/, secțiunea 13): forma shell „starts your `ENTRYPOINT` as a subcommand of `/bin/sh -c`, which does not pass signals”, deci executabilul „will not be the container's `PID 1`, and will not receive Unix signals”; `docker stop` trimite SIGTERM, apoi SIGKILL după 10 s.
  - Rulat pe `python:3.13-slim` (`docker stop`, cronometrat în secunde întregi): (a) `CMD python -u app.py` în formă shell, cu handler SIGTERM în aplicație → `/proc/1/cmdline` = `/bin/sh -c python -u app.py`, oprire ~10–11 s, handlerul nu rulează; același rezultat (10 s, exit 137) pentru `CMD python -u app.py && echo bye`. Pe Debian, `dash` NU face `exec` automat pentru comanda simplă. (b) forma exec cu handler → oprire în sub 1 s, „got SIGTERM”, exit 0. (c) forma exec FĂRĂ handler (`python -c "import time; time.sleep(300)"`) → 10 s, exit 137: PID 1 nu primește acțiunea implicită a SIGTERM, deci cade abia SIGKILL. (d) același program cu `docker run --init` → 0 s, exit 143 (tini transmite SIGTERM și acțiunea implicită funcționează).
  - ⚠️ O oprire făcută chiar în clipa pornirii (înainte ca Python să instaleze handlerul) a dat 10 s și 137 și cu forma exec; testul final așteaptă 2 s după pornire.
  - ✅ gunicorn / uvicorn instalează handler pentru SIGTERM (faptele din secțiunile 13 și 23); un script Python propriu nu. Celery: SIGTERM = warm shutdown, „The worker will finish all currently executing tasks before it actually terminates” (https://docs.celeryq.dev/en/stable/userguide/workers.html).
- ✅ **Healthcheck, probe, volume** (https://docs.docker.com/reference/dockerfile/ la `HEALTHCHECK`): `--interval` 30s, `--timeout` 30s, `--start-period` 0s, `--start-interval` 5s, `--retries` 3; starea inițială `starting`, un control reușit → `healthy`, după destule eșecuri → `unhealthy`; exit 0 = sănătos, 1 = nesănătos; o singură instrucțiune `HEALTHCHECK` per Dockerfile.
  - Rulat: `docker run -d --health-cmd false --health-interval 1s alpine sleep 60` → după 6 s `docker ps --format '{{.Status}}'` = `Up 6 seconds (unhealthy)`, iar `State.Status` rămâne `running`: Docker simplu nu repornește containerul.
  - Swarm: „The scheduler may reschedule your running service containers at any time if they become unhealthy or unreachable” (https://docs.docker.com/engine/swarm/services/). Nu am testat reprogramarea pe un healthcheck care eșuează, doar înlocuirea unui container șters (punctul 8).
  - Kubernetes (https://kubernetes.io/docs/concepts/workloads/pods/probes/): eșecul liveness → „the kubelet restarts that container”; eșecul readiness → controllerul „removes the Pod's IP address from the EndpointSlices of all Services that match the Pod”; eșecul startup → containerul e omorât și intră sub restart policy. Desfășurarea le pomenește doar pe primele două.
- ✅ **Compose: DNS, `localhost`, `depends_on`** (https://docs.docker.com/compose/how-tos/networking/, https://docs.docker.com/reference/compose-file/services/): Compose „sets up a single network for your app”, numită `<proiect>_default`; „containers can reach each other using the service name directly”; între servicii se folosește `CONTAINER_PORT`, iar portul gazdei „is only used when accessing the service from outside the network”; `depends_on` scurt nu așteaptă („With short syntax, Compose does not wait for dependency services to be "healthy"”); cu `condition: service_healthy` „Compose guarantees dependency services marked with `service_healthy` are "healthy" before starting a dependent service”; `healthcheck.test` ca șir = `CMD-SHELL` + șirul.
  - Rulat (Compose v5.6.0, servicii alpine): `db` cu healthcheck care devine verde după ~4 s și `api` cu `depends_on: db: {condition: service_healthy}` → `api` pornește abia după `db Healthy` (la ~7 s după `up`); din `api`, `ping db` rezolvă 172.18.0.2, iar `nc -zv localhost 5432` eșuează (cod 1): `localhost` e containerul `api`. Fără `start_period`, cu `interval: 1s` și 3 eșecuri implicite, `db` a fost declarat `unhealthy` înainte să fie gata și `up` s-a oprit cu „dependency failed to start” (de aceea healthcheck-urile au nevoie de `start_period`).
  - ⚠️ Exemplul cu `postgres:16` și `test: pg_isready` din desfășurare nu a fost rulat (imaginea Postgres nu a fost trasă); mecanismul e cel verificat mai sus cu alpine. Șirul `pg_isready` echivalează cu `CMD-SHELL pg_isready` (documentația).
- ✅ **Swarm, Kubernetes, ECS, EKS** (https://docs.docker.com/engine/swarm/, https://docs.docker.com/engine/swarm/services/, https://docs.aws.amazon.com/AmazonECS/latest/developerguide/Welcome.html, https://docs.aws.amazon.com/eks/latest/userguide/what-is-eks.html): „Docker Swarm mode is built into the Docker Engine”; pentru un serviciu declari numărul de taskuri, iar managerul compară starea reală cu cea declarată; actualizările se aplică incremental, cu rollback. ECS: „a fully managed container orchestration service”, capacitate pe EC2, Fargate („serverless”) sau on-premises. EKS: „a fully managed Kubernetes service”; în varianta standard „AWS manages the Kubernetes control plane”.
  - Rulat: `docker swarm init`, `docker service create --name api --replicas 3 alpine sleep 600` → `3/3`; după `docker rm -f` pe un container al serviciului, în câteva secunde `docker service ls` arată din nou `3/3`, iar `docker service ps` arată taskul vechi `Failed` și unul nou `Running`. Apoi `docker service rm` și `docker swarm leave --force`.
  - ⚠️ Un `docker service update --image alpine:3.19 api` a fost oprit („update paused due to failure or early termination of task”) în sandbox, deci rolling update-ul nu l-am văzut rulând; afirmația din desfășurare („rolling update și rollback”) vine din documentație. „Kubernetes e standardul industriei” e formularea punctului fișei (apreciere, nu fapt de versiune).
- ✅ **`python:slim` vs `python:alpine`** (https://hub.docker.com/_/python, https://peps.python.org/pep-0656/): `slim` „does not contain the common Debian packages contained in the default tag”, iar `pip install` din sursă poate pica fără uneltele de build; alpine „does use musl libc instead of glibc and friends” și „software will often run into issues depending on the depth of their libc requirements”; PEP 656 introduce etichetele `musllinux` pentru wheels pe sisteme musl, „works similarly to the perennial manylinux platform tags”.
  - Rulat (`pip install --dry-run --only-binary=:all:`, pip 26.2.2): `torch` pe `python:3.13-alpine` → „No matching distribution found for torch (from versions: none)”; pe `python:3.13-slim` → „Would install … torch …”. `psycopg2-binary` are azi wheel `musllinux_1_2_x86_64`: pe alpine se descarcă `psycopg2_binary-2.9.13-cp313-cp313-musllinux_1_2_x86_64.whl`. Deci „alpine rupe wheels” e adevărat doar pentru pachete fără `musllinux` (ca `torch`), nu general; de aceea desfășurarea spune „multe pachete populare au așa ceva, dar nu toate”.
  - Dimensiuni locale (`docker images`, Docker 29, containerd snapshotter): `python:3.13-slim` 178 MB, `python:3.13-alpine` 70,5 MB; nu apar în text.
  - `python:3.13-slim` are Debian 13 (trixie) (`/etc/os-release`).

**Erori de fapt în punctele fișei `docker`**: una corectată, în punctul 1. În `src/data_core.js` (`P.sheets.docker.points[0]`), „Imagine = layere read-only (câte unul per instrucțiune); container = …” → „Imagine = layere read-only (câte unul per instrucțiune care schimbă fișiere: `RUN`, `COPY`, `ADD`; `ENV` și `CMD` adaugă doar metadate); container = …” (rulat: `ENV` și `CMD` nu adaugă layer de sistem de fișiere). Grilele vechi (`dk-02`, explicația „Fiecare instrucțiune produce un layer”) folosesc formularea simplificată din documentația Docker (https://docs.docker.com/build/cache/) și au rămas neatinse. Precizări, nu erori (apar în desfășurări, punctele rămân): la punctul 5, exec form nu e de ajuns: PID 1 nu primește acțiunile implicite ale semnalelor, deci aplicația are nevoie de un handler SIGTERM sau de `--init`; la punctul 9, „alpine poate rupe wheels” e valabil doar pentru pachetele fără wheel `musllinux` (multe au azi); la punctul 6, Docker simplu doar marchează containerul `unhealthy`, nu îl repornește.
