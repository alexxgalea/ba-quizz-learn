## 29. Desfășurări `index`: B-tree, indexuri compuse, parțiale, pe expresie, tipuri, INCLUDE, CONCURRENTLY, EXPLAIN, index inversat; comparațiile cu C++ (tichetul 13; verificat 3 noiembrie 2026)

Python rulat pe 3.13.16 (cele 4 blocuri din `src/desf/index.md` rulează în `node tools/desf_examples.mjs`). PostgreSQL 16.15 rulat local (cluster temporar: `initdb` + `pg_ctl` ca utilizatorul `postgres`, tabele de 1 milion de rânduri, șters după). C++ compilat cu `g++ 13.3` (`-Wall`) și `clang++ 18` în `-std=c++17`; faptele despre standard vin din draftul de pe eel.is/c++draft (cppreference răspunde 403 din mediul de lucru). Exemplele SQL din desfășurări sunt blocuri `text` (nu rulează în check-ul de exemple), dar fiecare a fost rulat pe Postgres 16 la scriere. Faptele despre `CONCURRENTLY` și Alembic: și secțiunea 15.

- ✅ **Index și overhead** (https://www.postgresql.org/docs/16/indexes-intro.html): indexul e comparat cu cel de la finalul unei cărți; „After an index is created, the system has to keep it synchronized with the table. This adds overhead to data manipulation operations.”; „indexes that are seldom or never used in queries should be removed.”; „Indexes can also prevent the creation of heap-only tuples.” Planner-ul folosește indexul „when it thinks doing so would be more efficient than a sequential table scan”, iar `ANALYZE` trebuie rulat periodic pentru statistici.
- ✅ **B-tree** (https://www.postgresql.org/docs/16/indexes-types.html, https://www.postgresql.org/docs/16/btree-implementation.html): „B-trees can handle equality and range queries on data that can be sorted”; operatorii `< <= = >= >`, plus `BETWEEN`, `IN`, `IS NULL`; metoda implicită la `CREATE INDEX` e `btree` (https://www.postgresql.org/docs/16/sql-createindex.html). Structura: „multi-level tree structures”, pagini frunză și interne în formatul standard de pagină, „over 99% of all pages are leaf pages”; documentația nu dă numărul de chei pe pagină (desfășurarea spune doar „mai multe chei”). `block_size` = 8192 (rulat: `current_setting('block_size')`). Rulat: căutarea binară din exemplul 1 pe 10**6 chei face 20 de pași.
- ✅ **UPDATE, HOT, VACUUM** (https://www.postgresql.org/docs/16/storage-hot.html, https://www.postgresql.org/docs/16/routine-vacuuming.html): un HOT update cere două condiții, „The update does not modify any columns referenced by the table's indexes, not including summarizing indexes” și „There is sufficient free space on the page containing the old row”; atunci „New index entries are not needed”. `VACUUM` „removes dead row versions in tables and indexes”. Rulat (`fillfactor=70`, 2000 de UPDATE-uri): `n_tup_upd` = 2000, `n_tup_hot_upd` = 448 (HOT nu e garantat nici când coloanele indexate rămân neschimbate).
- ✅ **Cheie străină fără index** (https://www.postgresql.org/docs/16/ddl-constraints.html): „the declaration of a foreign key constraint does not automatically create an index on the referencing columns”, deși „it is often a good idea to index the referencing columns too” (DELETE / UPDATE pe tabela referită scanează tabela care referă). Rulat: `\d orders` cu `customer_id bigint REFERENCES customers` arată doar `orders_pkey`; `PRIMARY KEY` și `UNIQUE` creează index (`u_pkey`, `u_e_key`), iar cheia străină nu. Rulat pe 1 milion de rânduri: `WHERE customer_id = 7` fără index = `Parallel Seq Scan` (51 ms, `Rows Removed by Filter: 333000` pe worker), cu index = `Bitmap Index Scan` + `Bitmap Heap Scan` (2,7 ms). Django: „A database index is automatically created on the `ForeignKey`” (`db_index`, https://docs.djangoproject.com/en/5.2/ref/models/fields/).
- ✅ **Indexuri compuse** (https://www.postgresql.org/docs/current/indexes-multicolumn.html): „can be used with query conditions that involve any subset of the index's columns, but the index is most efficient when there are constraints on the leading (leftmost) columns”; „equality constraints on leading columns, plus any inequality constraints on the first column that does not have an equality constraint, will always be used to limit the portion of the index that is scanned”; constrângerile din dreapta „are checked in the index” dar nu reduc neapărat porțiunea scanată. Skip scan (PG 18): „Allow skip scans of btree indexes… multi-column btree indexes to be used in more cases such as when there are no restrictions on the first or early indexed columns” (https://www.postgresql.org/docs/release/18.0/); apare „when there are so few distinct `x` values that the planner expects the scan to skip over most of the index”. Rulat pe PG 16, index `(a, b)` pe 500.000 de rânduri (`a` cu 5 valori): `a = 2 AND b = 7` și `ORDER BY a, b LIMIT 5` = `Index Scan` pe interval; `b = 7` singur = `Index Scan` cu `Index Cond: (b = 7)` care parcurge tot indexul (cost 6630 față de 7703 pentru Seq Scan, deci planner-ul l-a ales, dar nu limitează intervalul); `ORDER BY b LIMIT 5` = `Seq Scan` + `Sort` (indexul nu dă ordinea după `b`).
- ✅ **Selectivitate și index parțial** (https://www.postgresql.org/docs/16/indexes-partial.html, https://www.postgresql.org/docs/16/runtime-config-query.html): „a query searching for a common value (one that accounts for more than a few percent of all the table rows) will not use the index anyway”; „a partial index can be used in a query only if the system can recognize that the WHERE condition of the query mathematically implies the predicate of the index”; la query-uri parametrizate potrivirea se face la planificare, deci „parameterized query clauses do not work with a partial index”. Valorile implicite: `seq_page_cost` 1,0, `random_page_cost` 4,0. Rulat (1 milion de rânduri: `done` 660.000, `open` 330.000, `pending` 10.000): `status = 'done'` cu index pe `status` = `Seq Scan`; `status = 'pending'` = `Bitmap Index Scan`; cu `CREATE INDEX ON orders (created_at) WHERE status = 'pending'`, `WHERE status = 'pending' ORDER BY created_at LIMIT 20` = `Index Scan using orders_pend_created` fără `Sort`, iar același query cu `'done'` = `Seq Scan` + `Sort`; indexul parțial pe `(id)` are 240 kB față de 21 MB pentru cheia primară.
- ✅ **Index pe expresie** (https://www.postgresql.org/docs/16/indexes-expressional.html, https://www.postgresql.org/docs/16/sql-createindex.html): exemplul `lower(col1)`; „Index expressions are relatively expensive to maintain, because the derived expression(s) must be computed for each row insertion and non-HOT update”; „All functions and operators used in an index definition must be 'immutable'”. Rulat: `WHERE lower(email) = 'ana2@x.ro'` cu index doar pe `email` = `Parallel Seq Scan`, cu `(lower(email))` = `Index Scan`; `CREATE INDEX ON orders ((created_at::date))` pe `timestamptz` pică (`ERROR 42P17: functions in index expression must be marked IMMUTABLE`); aceeași expresie pe o coloană `timestamp` (fără fus) merge; `((created_at AT TIME ZONE 'UTC')::date)` pe `timestamptz` merge. Django: `Index(Lower("title").desc(), "pub_date", name="lower_title_date_idx")` (https://docs.djangoproject.com/en/5.2/ref/models/indexes/); `Meta.indexes` cu `Lower("email")` urmează aceeași formă (nerulat).
- ✅ **Tipuri de index** (https://www.postgresql.org/docs/16/indexes-types.html): Hash: „store a 32-bit hash code derived from the value of the indexed column. Hence, such indexes can only handle simple equality comparisons”; GIN: „inverted indexes… appropriate for data values that contain multiple component values, such as arrays. An inverted index contains a separate entry for each component value”; GiST: infrastructură cu mai multe strategii, operatori geometrici și căutare „nearest-neighbor” (`ORDER BY location <-> point '(…)' LIMIT 10`); BRIN: „store summaries about the values stored in consecutive physical block ranges of a table. Thus, they are most effective for columns whose values are well-correlated with the physical order of the table rows” (min și max pe bloc). Rulat pe 1 milion de rânduri inserate în ordinea timpului: B-tree pe `timestamptz` 21 MB, BRIN 24 kB, Hash 32 MB (mai mare decât B-tree-ul), GIN pe `jsonb` 2,1 MB față de 39 MB pentru B-tree pe `jsonb`; `payload @> '{"type": "login"}'` folosește GIN (`Bitmap Index Scan`), iar cu doar un B-tree pe `payload` rămâne `Seq Scan` chiar și cu `enable_seqscan = off` (B-tree nu răspunde la `@>`); `tags @> ARRAY['t5']` folosește GIN pe array; `area && tstzrange(...)` folosește GiST; `at = …` folosește Hash, iar un interval pe `at` cu doar Hash rămâne `Seq Scan`.
- ✅ **INCLUDE și Index Only Scan** (https://www.postgresql.org/docs/16/indexes-index-only-scans.html, https://www.postgresql.org/docs/16/sql-createindex.html): coloanele `INCLUDE` sunt „non-key”, nu pot fi folosite la căutarea prin index, iar scanarea poate returna conținutul lor fără acces la tabel; „the query must reference only columns stored in the index”; B-tree, GiST și SP-GiST suportă coloane incluse, nu și expresii; „If an index tuple exceeds the maximum size allowed for the index type, data insertion will fail”. Index-only scan verifică harta de vizibilitate; „it will be a win only if a significant fraction of the table's heap pages have their all-visible map bits set”, iar `VACUUM` o ține la zi (https://www.postgresql.org/docs/16/routine-vacuuming.html). Rulat: `CREATE INDEX ON orders (customer_id) INCLUDE (total, status)` + `VACUUM`: `SELECT total, status … WHERE customer_id = 7` = `Index Only Scan`, `Heap Fetches: 0`; același query cu `payload` în plus (necuprinsă) = `Bitmap Heap Scan`.
- ✅ **CREATE INDEX CONCURRENTLY** (https://www.postgresql.org/docs/16/sql-createindex.html; secțiunea 15): un `CREATE INDEX` obișnuit blochează `INSERT`/`UPDATE`/`DELETE` până se termină construirea; `CONCURRENTLY` face „two scans of the table” și așteaptă tranzacțiile existente; „a regular `CREATE INDEX` command can be performed within a transaction block, but `CREATE INDEX CONCURRENTLY` cannot”; la eșec rămâne un index „invalid”, ignorat la interogări dar care costă la scrieri; recuperare: `DROP INDEX` și reluare, sau `REINDEX INDEX CONCURRENTLY`. Rulat: `CREATE UNIQUE INDEX CONCURRENTLY` peste valori duplicate pică cu „Key (v)=(1) is duplicated” și lasă `"dup_v" UNIQUE, btree (v) INVALID` în `\d`, iar `DROP INDEX` îl scoate. Alembic 1.20.1 + SQLAlchemy 2.1.6 pe Postgres 16: `with ctx.autocommit_block(): op.create_index("m_c_idx", "m", ["c"], postgresql_concurrently=True)` creează indexul valid; același `op.create_index(..., postgresql_concurrently=True)` într-o tranzacție pică cu `ActiveSqlTransaction: CREATE INDEX CONCURRENTLY cannot run inside a transaction block`.
- ✅ **EXPLAIN** (https://www.postgresql.org/docs/16/sql-explain.html): `ANALYZE` „Carry out the command and show actual run times”; „the statement is actually executed when the ANALYZE option is used”, iar pentru `INSERT`/`UPDATE`/`DELETE` se recomandă `BEGIN; EXPLAIN ANALYZE …; ROLLBACK;`; `BUFFERS` raportează blocurile partajate „hit” (găsite în cache) și „read”; în PG 16 `BUFFERS` e `FALSE` implicit. PG 18: „Automatically include `BUFFERS` output in `EXPLAIN ANALYZE`” (https://www.postgresql.org/docs/release/18.0/). Rulat: `EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM orders WHERE id = 5` = `Index Scan using orders_pkey`, `Index Cond: (id = 5)`, `Buffers: shared hit=3 read=4` (cache rece); un `UPDATE` sub `EXPLAIN (ANALYZE)` într-o tranzacție urmată de `ROLLBACK` lasă rândurile neschimbate; cu `Seq Scan`, `Rows Removed by Filter` arată rândurile citite degeaba.
- ✅ **Elasticsearch: index și index inversat** (https://www.elastic.co/blog/what-is-an-elasticsearch-index, https://www.elastic.co/docs/solutions/search/full-text/how-full-text-works, https://www.elastic.co/guide/en/elasticsearch/reference/current/analysis.html): „An Elasticsearch index is a logical namespace that holds a collection of documents”, cu o analogie cu tabelul din RDBMS (cluster ≈ bază de date, index ≈ tabel, document ≈ rând); „An inverted index is a data structure that maps each token to the documents that contain it”; dicționarul de termeni e „a sorted list of all unique terms”, iar lista de postări ține, pentru fiecare termen, id-urile documentelor (plus frecvență și poziții opționale); textul trece mai întâi printr-un analyzer (tokenizare: „in most cases, these tokens are individual words”). Pagina `documents-indices` nu definește indexul inversat; folosită doar pentru „index = unitate de stocare”. Exemplul 11 (index inversat în Python, `[0, 1]` pentru „login”) rulează în check-ul de exemple.
- ✅ **C++ (`-std=c++17`, g++ 13.3 și clang++ 18; `t.cpp`)**: `std::map`: `find`, `lower_bound`, `insert` sunt „Logarithmic” (draft, [associative.reqmts]); standardul nu cere arbore roșu-negru, dar libstdc++ folosește `_Rb_tree` (`/usr/include/c++/13/bits/stl_map.h`). `std::unordered_map::find`: „Average case O(1), worst case O(b.size())”, iar ordinea de iterare nu e specificată ([unord.req]). `std::pair` se compară lexicografic (`operator<`; în C++20 prin `operator<=>`: primul membru, apoi al doilea): `map<pair<int, string>, int>` cu `lower_bound({2, ""})` dă exact blocul `(2,x) (2,y)`, iar filtrarea după al doilea câmp parcurge toată harta (2 potriviri din 4). Compilat: `map.lower_bound(15)`..`upper_bound(30)` dă `20 30`; `unordered_map<int, string>` are `at(20)` = `b`, `count(15)` = 0 și nicio interogare de interval; `unordered_map<string, vector<int>>` umplut din cuvintele documentelor dă `inv["login"]` = `1 2`; `map<string,int>` cu cheia `"Ana@x.ro"` nu găsește `"ana@x.ro"` (`count` = 0).
- ⚠️ **Nerulat, doar din documentație**: pagina Django pentru `Meta.indexes` cu `Lower("email")` (exemplul oficial e cu `Lower("title")`); structura internă a dicționarului de termeni din Lucene (desfășurarea 11 spune doar „sortat”, cum zice documentația); numărul de chei pe o pagină de B-tree (documentația nu îl dă).

**Erori de fapt în punctele fișei `index`**: niciuna găsită; punctele nu au fost modificate. Cele 11 puncte au fost recitite față de sursele de mai sus și față de rulări. Precizări, nu erori: la punctul 1, „O(log n)” descrie numărul de pași, iar un nod de B-tree e o pagină de disc (nu un nod binar); la punctul 2, un `DELETE` nu scoate imediat intrările din index, le curăță `VACUUM`, iar un `UPDATE` poate evita indexurile (HOT); la punctul 4, `b = ?` singur poate folosi totuși indexul `(a, b)`, dar parcurgând tot indexul (observat pe PG 16, cu `a` de puține valori distincte), iar PG 18 poate sări peste valorile lui `a`; la punctul 6, `created_at::date` merge în index doar pe `timestamp` (fără fus), nu pe `timestamptz` (eroare `IMMUTABLE`); la punctul 7, „tabele uriașe ordonate fizic” înseamnă că valorile urmează ordinea fizică a rândurilor; la punctul 8, câștigul depinde de harta de vizibilitate (`VACUUM`); la punctul 10, din PG 18 `BUFFERS` e inclus automat în `EXPLAIN ANALYZE`.
