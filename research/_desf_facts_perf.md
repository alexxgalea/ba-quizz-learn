## 38. Desfășurări `perf`: profilare, algoritmi, loturi de I/O, vectorizare, memorie și generatori, backpressure, procese și `chunksize`, legea lui Amdahl; comparațiile cu C++ (tichetul 19; verificat 3 noiembrie 2026)

Rulat pe Linux (4 core-uri, 16 GB), Python 3.13.16, NumPy 2.5.3, `g++ 13.3` (`-std=c++17`, `-O2`), `valgrind` instalat, py-spy 0.4.3, line_profiler 5.1.0 și SnakeViz 2.2.2 (instalate într-un venv temporar din PyPI). Cele 4 blocuri `python` din `src/desf/perf.md` (punctele 2, 5, 6 și 8) rulează în `node tools/desf_examples.mjs`; blocurile `text` (1, 3, 4, 7) sunt ieșiri reale, rulate la scriere, cu editările notate mai jos. Docs.python.org servește acum documentația pentru 3.15; faptele de versiune sunt verificate și pe 3.13 (`/3.13/`). Cifrele de timp depind de mașină și variază mult de la o rulare la alta (vezi nota la punctul 7). cppreference răspunde 403 din mediul de lucru; faptele C++ vin din draftul N4659 și din rulare.

**1. Profilare**
- ✅ `cProfile`: „recommended for most users; it's a C extension with reasonable overhead that makes it suitable for profiling long-running programs”; `python -m cProfile [-o output_file] [-s sort_order] (-m module | myscript.py)`; `tottime` = „the total time spent in the given function (and excluding time made in calls to sub-functions)”; `cumtime` = „the cumulative time spent in this and all subfunctions”; `ncalls` = numărul de apeluri (https://docs.python.org/3.13/library/profile.html). Profilarea deterministă monitorizează „all function call, function return, and exception events”, cea statistică „periodically samples the effective instruction pointer” și are de regulă mai puțin overhead (https://docs.python.org/3/library/profile.html). ⚠️ Pe paginile 3.15, `cProfile` rămâne ca alias pentru `profiling.tracing`, iar cu `profiling.sampling` apare un profiler statistic în biblioteca standard; desfășurarea nu pomenește asta (Alex lucrează cu 3.13 / 3.12).
- ✅ Rulat: `python3 -m cProfile -s tottime job.py` pe un script cu `parse` apelat de 20 000 de ori. Tabelul din exemplu e ieșirea reală, cu coloanele `percall` și `filename:lineno` scoase și cu numele funcțiilor scurtate (`job.py:2(<genexpr>)` → `genexpr`, antetul `funcția` → `func`, `{built-in method builtins.sum}` → `sum`); valorile (`200000 / 0.060 / 0.060`, `20000 / 0.044 / 0.104`, `20000 / 0.012 / 0.116`, `1 / 0.007 / 0.122`) sunt cele măsurate. Fiecare `parse` a avut `tottime` mic și `cumtime` mare: timpul e în subapeluri.
- ✅ SnakeViz: „browser-based graphical viewer for Python's cProfile output”, folosit cu `python -m cProfile -o program.prof my_program.py` și `snakeviz program.prof` (https://jiffyclub.github.io/snakeviz/). Instalat (2.2.2); nu l-am deschis (browser).
- ✅ py-spy: „a sampling profiler for Python programs”, funcționează fără „restarting the program or modifying the code in any way”, rulează în afara procesului, cu trei subcomenzi `record`, `top`, `dump` și `--pid`; pe Linux „the default configuration is to require root permissions when attaching to a process that isn't a child”; în Docker se adaugă `--cap-add SYS_PTRACE`, în Kubernetes capability-ul `SYS_PTRACE` (https://github.com/benfred/py-spy). Rulat (root, procesul `busy.py` pornit separat): `py-spy dump --pid` a afișat `Thread … (idle)  wait (busy.py:7)  <module> (busy.py:9)`; `py-spy record -d 2 -f raw` a scris `<module> (busy.py:9);slow (busy.py:4) 102` (102 eșantioane, 0 erori). `py-spy top` nu merge fără terminal (`Not a tty`); nerulat.
- ✅ line_profiler 5.1.0: „a module for doing line-by-line profiling of functions”; `kernprof -lv lp.py` a produs tabelul `Line # / Hits / Time / Per Hit / % Time / Line Contents` (86,6% pe lista comprehensions, 13,4% pe `sum`); `@profile` se adaugă de `kernprof`, fără import (README-ul curent preferă `from line_profiler import profile` cu `LINE_PROFILE=1`). Desfășurarea spune doar „cronometrează linie cu linie funcțiile decorate cu `@profile`”.
- ✅ tracemalloc: „traces memory blocks allocated by Python”, `start(nframe=1)`, `take_snapshot()`, `statistics('lineno')`, `get_traced_memory()` → `(current, peak)`, `reset_peak()` (https://docs.python.org/3/library/tracemalloc.html). Desfășurarea îl menționează doar ca „arată cine alocă memorie”.
- ✅ **C++ (Linux `perf`)**: `perf record` „runs a command and collects a performance counter profile into `perf.data`”; `-g` = call graph, `-F` = frecvență de eșantionare, `-p PID` = procese existente (https://man7.org/linux/man-pages/man1/perf-record.1.html). ⚠️ `perf` lipsește din mediu, deci nerulat. Callgrind (`valgrind --tool=callgrind`) „records the call history among functions in a program's run as a call graph”, numără instrucțiuni executate (https://valgrind.org/docs/manual/cl-manual.html); am pornit `valgrind --tool=callgrind` pe un program mic (a raportat `I refs: 427,839`), fără să citesc raportul. Echivalența `perf record` ≈ `py-spy` (eșantionare) și `callgrind` ≈ `cProfile` (urmărește apelurile) este o analogie de metodă: callgrind numără instrucțiuni, nu timp.
- ✅ Python și `perf`: „Normally `perf` only sees native C symbols. Every Python function shows up as `_PyEval_EvalFrameDefault`”; „The `perf` trampoline mode has been available since Python 3.12”; se activează cu `python -X perf`, `PYTHONPERFSUPPORT=1` sau `sys.activate_stack_trampoline("perf")` (https://docs.python.org/3/howto/perf_profiling.html). Nerulat (fără `perf`).

**2. Algoritmi și structuri**
- ✅ Complexități: `x in list` O(n), `x in set` O(1) în medie și O(n) în cel mai rău caz, `deque.popleft()` O(1), `list.pop(0)` și `list.insert(0, x)` O(n) (https://wiki.python.org/moin/TimeComplexity, redirect). CPython: listele sunt „really variable-length arrays, not Lisp-style linked lists … a contiguous array of references to other objects”; dicționarele sunt tabele hash redimensionabile (https://docs.python.org/3/faq/design.html).
- ✅ Rulat: pentru `xs = list(range(10_000))` și `s = set(xs)`, 1000 de căutări ale lui `9999` au durat de ~1400 de ori mai mult în listă; exemplul afirmă doar `run(xs) > 50 * run(s)` (500 de căutări în fiecare), adevărat cu mare marjă.
- ✅ C++ (rulat, `g++ -O2 -std=c++17`): 20 000 de căutări ale ultimului element în 10 000 de întregi au durat 99,5 ms cu `std::find` pe `std::vector<int>` și 0,03 ms cu `std::unordered_set::count`. `std::deque::pop_front()` este constant ([deque.modifiers], N4659; nerulat). ⚠️ Am încercat și n = 8: `unordered_set` a ieșit mai rapid decât `find` (5,6 ms față de 14,7 ms la 2 milioane de căutări), deci **nu** am afirmat că un `vector` bate un set la n mic.
- ✅ „Unde nu ține”: lista Python e un tablou contiguu de **referințe**, iar fiecare `int` e un obiect separat (FAQ-ul de design de mai sus), în timp ce `std::vector<int>` ține valorile contigue.

**3. I/O în loturi**
- ✅ Rulat (sqlite3, bază pe disc, 2 000 de rânduri): `insert` + `commit` pe rând 2,995 s, `executemany` + un singur `commit` 0,0042 s. În exemplu: `3,0 s` și `0,004 s`. ⚠️ Măsoară costul unui `commit` (scriere pe disc), nu un round-trip de rețea; sqlite e local. Nu am măsurat Postgres.
- ✅ Redis pipelining: „issuing multiple commands at once without waiting for the response to each individual command”; cu 10 000 de `PING` pe loopback, 1,185 s fără pipelining și 0,251 s cu (≈ 5 ori, Ruby, Mac, cifre ale autorilor); serverul pune răspunsurile în coadă în memorie, deci se trimit loturi de ~10 000 de comenzi (https://redis.io/docs/latest/develop/using-commands/pipelining/). Nerulat (fără Redis în mediu).
- ✅ psycopg 3: COPY este „one of the most efficient ways to load data into the database”; `cursor.copy("COPY … FROM STDIN")` cu `write_row()` (https://www.psycopg.org/psycopg3/docs/basic/copy.html). Pagina nu compară COPY cu `INSERT`; desfășurarea nu dă cifre. Vezi și `src/desf/postgres.md`.
- ✅ httpx: `Client` folosește connection pooling și refolosește conexiunea TCP între cereri; evită handshake-urile repetate, reduce CPU, round-trip-uri și congestia rețelei (https://www.python-httpx.org/advanced/clients/).
- ⚠️ Nerulat / neverificat pe pagină: `bulk_create` și `iterator()` din Django (pagina QuerySet era prea lungă pentru citirea completă); desfășurarea nu le menționează.

**4. CPU**
- ✅ Rulat (NumPy 2.5.3, 1 000 000 de numere): `for i in range(n): s += i*i` — minim din 3 rulări 0,164 s; `(x * x).sum()` pe `np.arange(n, dtype=np.int64)` — minim din 20 de rulări 0,0020 s (prima rulare a fost mai lentă, 0,05 s, din cauza încălzirii). În exemplu: `0,16 s` și `0,002 s`; rezultatele au fost egale.
- ✅ orjson: `dumps()` întoarce `bytes`, „something like 10x as fast as json” (măsurătorile autorului) la serializare și „2x” la `loads`; construirea cere Rust; README-ul nu spune explicit „scris în Rust” (https://github.com/ijl/orjson). Desfășurarea spune „JSON în Rust”, fără cifre.
- ✅ `re`: „The compiled versions of the most recent patterns passed to `re.compile()` and the module-level matching functions are cached, so programs that use only a few regular expressions at a time needn't worry about compiling regular expressions”; reutilizarea obiectului compilat „is more efficient when the expression will be used several times” (https://docs.python.org/3/library/re.html). Rulat: `re.compile(r"\d+") is re.compile(r"\d+")` → `True` (cache). Desfășurarea spune doar „compilezi o dată”.
- ✅ Rulat: `functools.lru_cache` pe `fib(30)`: `CacheInfo(hits=28, misses=31, maxsize=None, currsize=31)`.
- ⚠️ Nerulat, doar numit: pandas și Polars (vectorizare). Am încercat și un contra-exemplu C++ (autovectorizare cu `-O3`): `g++ 13.3 -fopt-info-vec` nu a raportat nimic pentru bucla de înmulțire pe `long`, așa că desfășurarea nu face nicio afirmație despre SIMD.

**5. Memorie**
- ✅ Rulat (`tracemalloc`): `sum([i for i in range(10**6)])` a avut vârful de 40 440 496 de octeți, `sum(i for i in range(10**6))` după `reset_peak()` 888 de octeți (`a > 100 * b` → `True`).
- ✅ SQLAlchemy 2.0: `yield_per` „is equivalent to manually setting the `stream_results` option” și selectează cursoare server-side „where the backend supports them”, aducând rânduri în loturi; implicit, pe PostgreSQL și MySQL cursorul e bufferizat („the full set of results is pulled into memory”); nu apela `Result.all()` cu `yield_per` (https://docs.sqlalchemy.org/en/20/core/connections.html). Nerulat contra unui Postgres. Vezi `src/desf/sqlalchemy.md`.

**6. Backpressure**
- ✅ `queue.Queue(maxsize)`: „Insertion will block once this size has been reached, until queue items are consumed”; `put_nowait()` ridică `Full`; `full()` (https://docs.python.org/3/library/queue.html). Rulat: cu `maxsize=2` și două `put`, `q.full()` → `True`, iar `put_nowait(3)` ridică `queue.Full`. `asyncio.Queue(maxsize)`: „`await put()` blocks when the queue reaches maxsize until an item is removed by `get()`”; `put_nowait` ridică `QueueFull` (https://docs.python.org/3/library/asyncio-queue.html); nerulat.
- ⚠️ Nerulat: `prefetch` din RabbitMQ ca formă de backpressure (secțiunea 13 din `interview-facts.md`: `basic.qos` limitează mesajele neconfirmate).

**7. Procese și `chunksize`**
- ✅ `Executor.map(fn, *iterables, timeout=None, chunksize=1, buffersize=None)`: „this method chops iterables into a number of chunks which it submits to the pool as separate tasks … For very long iterables, using a large value for chunksize can significantly improve performance compared to the default size of 1” (https://docs.python.org/3/library/concurrent.futures.html). `Pool.map` fără `chunksize` îl calculează în sursa CPython (`divmod(len(iterable), len(self._pool) * 4)`, plus 1 dacă există rest); citit în `multiprocessing/pool.py` din mediu.
- ✅ Rulat (4 core-uri; `f(x) = x + 1` pe 200 000 de numere): `for` simplu 0,045 s; `ProcessPoolExecutor(4).map` cu `chunksize=1` (și cu valoarea implicită) 55 s (într-o altă rulare, 53 s și cu `Pool.map(chunksize=1)` 15–19 s); cu `chunksize=1000` 0,108 s; `Pool.map` cu valoarea implicită 0,052 s. Cifrele variază mult între rulări; exemplul rotunjește: 55 s, 0,1 s, 0,05 s. Concluzia stabilă: `chunksize=1` face paralelizarea de sute de ori mai lentă decât un `for`.
- ✅ Argumentele și funcția trebuie să poată fi serializate (pickle) pentru `ProcessPoolExecutor`; „A function defined in a REPL or a lambda should not be expected to work”. Metoda implicită de pornire: schimbată în 3.14 din `fork` în `forkserver` pe POSIX; pe 3.13 e `fork` pe Linux (inferat din notă); desfășurarea nu depinde de ea.
- ✅ C++: `std::thread` partajează spațiul de adrese al procesului (standard, [thread.thread]); nu am compilat un exemplu pentru această afirmație. Transportul între procese (`fork` + pipe) cere serializare explicită: cunoaștere generală.

**8. Legea lui Amdahl**
- ✅ S = 1 / ((1 − p) + p / s); limita pentru s → ∞ este 1 / (1 − p), adică 10 pentru p = 0,9 (https://en.wikipedia.org/wiki/Amdahl%27s_law; sursă secundară, formula e standard). Rulat: `amdahl(.9, 8)` rotunjit la două zecimale dă `4.71`, iar `amdahl(.9, 1e9)` dă `10.0`.

**Erori de fapt în punctele fișei `perf`**: niciuna găsită; punctele nu au fost modificate. Precizări, nu erori: la punctul 1, `py-spy` nu cere întotdeauna root: pe Linux e nevoie de root sau de `ptrace_scope` relaxat, iar în container de `SYS_PTRACE`; la punctul 3, `COPY` și pipelining reduc costul fix per rând, dar pipeline-urile uriașe consumă memorie pe server (loturi de ~10 000); la punctul 4, `re` are un cache al modelelor recente, deci `re.compile` contează în principal pentru modelele folosite des (docs), nu e o optimizare spectaculoasă; la punctul 7, `ProcessPoolExecutor.map` pornește cu `chunksize=1`, iar `Pool.map` își calculează singur unul, deci „chunksize mare” e o necesitate mai ales la executor; „fiecare proces are propriul GIL” e adevărat pentru procese separate (la sub-interpretoare, din 3.12, GIL-ul e per interpretor).
